Ratchet - Portable CDI-based Job Scheduler

Ratchet is a lightweight, portable job scheduling library for Jakarta EE applications. It provides a clean API for background job scheduling with pluggable store implementations (MySQL, PostgreSQL, MongoDB).

Core Modules

  • ratchet-api - Public API, events, enums, and SPI interfaces. Zero runtime dependencies.
  • ratchet - Reference Implementation with CDI integration, lambda analysis, and the execution engine.
  • ratchet-store-core - Shared persistence abstractions (entities, repositories, base interfaces).
  • ratchet-store-mysql - MySQL store implementation with DDL schema.
  • ratchet-store-postgresql - PostgreSQL store implementation with DDL schema.
  • ratchet-store-mongodb - MongoDB store implementation.

Quick Start

Schedule a job with a simple lambda expression: 

@Inject JobSchedulerService scheduler;

// Schedule a job to run immediately
scheduler.enqueueNow(() -> myService.processData())
  .withMaxRetries(3)
  .submit();

// Schedule with a delay
scheduler.schedule(Duration.ofMinutes(5), () -> myService.sendReport())
  .submit();

// Schedule recurring (cron)
scheduler.scheduleRecurring("0 9 * * MON-FRI", ZoneId.of("US/Eastern"),
    () -> myService.dailyCheckup())
  .submit();

// Chain jobs
scheduler.enqueue(() -> myService.step1())
  .then(() -> myService.step2())
  .then(() -> myService.step3())
  .submit();

Key Features

  • Portable CDI Integration - Works with any Jakarta EE container (WildFly, Payara, Open Liberty)
  • Lambda-Based API - Simple, type-safe job definitions via lambdas and method references
  • Durable Execution - Jobs persisted in the database, recoverable after crashes
  • Multi-Node Support - Horizontal scaling with distributed coordination
  • Flexible Retry Logic - Customizable retry policies with exponential backoff
  • Recurring Jobs - Cron-based scheduling with timezone support
  • Job Chains & Workflows - Sequential execution, branching, and batch processing
  • Circuit Breaker - Built-in resilience protection (no external dependencies)
  • Resource Permits - Rate limiting and capacity management
  • Comprehensive Observability - Event publishing, execution tracking, and detailed logging

Job Lifecycle

Each job follows this execution path:

  1. Submit - Schedule job via API (persisted to database)
  2. Poll - Poller claims jobs from database in batches
  3. Execute - JobTask runs the job payload with validation, permits, timeouts
  4. Success/Failure - Complete successfully, retry with backoff, or move to DLQ
  5. Post-Processing - Handle chains, workflows, callbacks, and event publication

Resilience & Reliability

  • Crash Recovery - Orphaned jobs automatically recovered via health checks
  • Retry Logic - Configurable retry policies with exponential backoff (NONE/FIXED/EXPONENTIAL)
  • Circuit Breaker - Lightweight state machine protecting against cascading failures
  • Timeouts - Per-job execution timeouts with watchdog interruption
  • Graceful Shutdown - Drain mode prevents new claims, allows running jobs to complete

SPI (Service Provider Interface)

Ratchet defines several extension points for customization:

  • RetryPolicy - Customize retry decisions and delay calculations
  • ResilienceStrategy - Pluggable circuit breaker and resilience implementations
  • BeanResolver - Resolve job target beans (CDI, reflection, custom factories)
  • ExecutorProvider - Supply custom executor services (virtual threads, custom pools)
  • ErrorSanitizer - Customize exception message filtering before persistence
  • ClassPolicy - Security policy for class loading and payload validation
  • NodeIdentityProvider - Provide unique node identifiers for distributed coordination

Architecture

Ratchet implements a pull-based architecture where workers pull jobs when ready, enabling natural backpressure and horizontal scalability. All job state is stored durably in the database, allowing crash recovery and multi-node deployments.

  • Pull-Based Model - Workers pull when ready, not push
  • Database-Centric - All state in DB, no in-memory queues
  • Adaptive Polling - Poller adjusts frequency based on job availability
  • Distributed Coordination - DB locks for leader election and global operations
